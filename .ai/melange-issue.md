## `let rec` with non-function and `lazy` bindings generates JavaScript with forward reference error

### Melange version

Melange 5.1.0-414 (Using OCaml:4.14.1+Melange)

### Description

When compiling `let rec x = ... y and y = lazy ...` where `x` is a non-function recursive value that references `y` (a lazy binding), Melange generates JavaScript where `y` is referenced before its `const` declaration, causing a `ReferenceError` at runtime.

The code compiles without error and is valid OCaml (works correctly with the native compiler).

### Minimal reproducer

```ocaml
(* rec_value.ml *)
type t = { next : t Lazy.t }

let r =
  let rec a = { next = b }
  and b = lazy { next = lazy a }
  in
  a
```

Native OCaml: compiles and runs correctly.

Melange: compiles without error, but the generated JavaScript fails at runtime.

### Generated JavaScript

```javascript
// Generated by Melange
'use strict';

const Caml_obj = require("melange.js/caml_obj.js");

let a = {};

Caml_obj.update_dummy(a, {
  next: b          // <-- ReferenceError: Cannot access 'b' before initialization
});

const b = {        // <-- 'b' is declared here, after it's used above
  LAZY_DONE: false,
  VAL: (function () {
    return {
      next: {
        LAZY_DONE: true,
        VAL: a
      }
    };
  })
};

const r = a;

module.exports = {
  r,
}
```

### Problem

Melange emits the `Caml_obj.update_dummy(a, { next: b })` call *before* the `const b = ...` declaration. In JavaScript, `const` (and `let`) bindings are in a temporal dead zone until their declaration is reached, so referencing `b` before its `const` statement causes:

```
ReferenceError: Cannot access 'b' before initialization
```

### Expected behavior

Either:
- Emit the bindings in an order that avoids the forward reference (e.g., emit `b` first since it's a lazy value that doesn't immediately need `a`), or
- Use `var` instead of `const`/`let` for these mutually recursive bindings (since `var` is hoisted), or
- Wrap the forward reference in a thunk so it's not evaluated eagerly.

### Real-world impact

This prevents using the [jsont](https://github.com/dbuenzli/jsont) library with Melange. jsont uses this pattern internally for its recursive JSON type combinator:

```ocaml
let json, json_array, mem_list, json_object =
  let rec elt = Repr.Rec any
  and array_map = lazy begin ... end
  and object' = lazy begin ... end
  and any = lazy begin ... end
  in
  Lazy.force any, Lazy.force array, Lazy.force mems, Lazy.force object'
```

### Root cause analysis

The issue is in `jscomp/core/lam_compile.ml`, function `compile_recursive_let` (line ~238),
specifically the interaction between **Case B** (line ~315) and **Case D** (line ~389).

#### Key code paths in `compile_recursive_let`

| Case | Condition | Behavior | JS output |
|------|-----------|----------|-----------|
| **A** (line 255) | `Lfunction` | Direct function declaration | `const f = function(...){}` |
| **B** (line 315) | `Pmakeblock` with all args being `Lfunction` or `Lconst` | Direct `const` declaration (Alias) | `const b = {LAZY_DONE: false, VAL: fn}` |
| **C** (line 336) | `Pmakeblock(Blk_record/constructor)` with args all self-ref or external | Inline dummy + field sets | `let a = {}; a.next = b;` |
| **D** (line 389) | General `Pmakeblock` (catch-all) | `update_dummy` pattern with hoisted declaration | `let a = {}; ... update_dummy(a, {...})` |

#### What happens for `let rec a = {next=b} and b = lazy {next=lazy a}`:

1. **SCC analysis** (`lam_scc.ml:scc_bindings`): Both `a` and `b` are in the same SCC
   (they reference each other). `sort_single_binding_group` keeps order `[a, b]` since
   neither is a function.

2. **`compile_recursive_lets_aux`** uses `List.fold_right` on `[a, b]`:
   - Processes `b` first (right-to-left): `lazy` block → `Pmakeblock` with args
     `[Lconst(false); Lfunction(...)]` → **Case B** matches (`args_either_function_or_const`
     is true) → emits `const b = {LAZY_DONE: false, VAL: fn}`, returns `declare_ids = []`
   - Then processes `a`: `{next=b}` → `Pmakeblock(Blk_record)` with args `[Lvar b]` →
     **Case C** guard fails because `b` IS in `all_bindings` → falls through to
     **Case D** → compiles RHS eagerly → emits `update_dummy(a, {next: b})`,
     returns `declare_ids = [let a = {}]`

3. **Assembly**: `fold_right` result is `output_code = code_a ++ code_b`,
   `ids = [let a = {}]`. Final output: `[let a = {}] ++ [update_dummy(a, {next: b})] ++ [const b = {...}]`

4. **Bug**: `update_dummy(a, {next: b})` eagerly reads `b`, but `b` is declared
   with `const` later → **temporal dead zone → ReferenceError**.

### Why Case B is wrong for `b` here

Case B treats `b` as a simple non-recursive value because its immediate args are all
`Lfunction`/`Lconst`. This is correct when `b` is standalone or when no other binding
in the same SCC group eagerly references `b`. But when `a` uses `update_dummy` which
eagerly evaluates `{next: b}`, the `const b` declaration must come BEFORE the
`update_dummy(a, ...)` call.

### Proposed fix

**Option 1 (Preferred): Make Case B also use dummy+update_dummy when the binding is
referenced by other bindings in the same `all_bindings` group.**

When `b`'s identifier is referenced by any other binding in `all_bindings` that will
be compiled with `update_dummy` (i.e., references it eagerly), `b` should also use the
dummy pattern so its declaration is hoisted alongside `a`'s dummy.

The condition for Case B should be strengthened: only match if no other binding in
`all_bindings` eagerly references this identifier. This can be checked by seeing if
the identifier appears as an eager (non-function-body) reference in any other binding.

A simpler conservative check: if ANY other binding in `all_bindings` references this
identifier (at any depth), use the dummy pattern. This is safe because `update_dummy`
works correctly for lazy blocks.

**Expected correct output:**
```javascript
let a = {};
let b = {};
Caml_obj.update_dummy(a, { next: b });
Caml_obj.update_dummy(b, { LAZY_DONE: false, VAL: function() { ... } });
const r = a;
```

**Option 2: Reorder output in `compile_recursive_lets_aux`** so that Case B (Alias)
declarations are emitted before Case D (`update_dummy`) code. This is more fragile.

**Option 3: Use `var` instead of `const`/`let`** for recursive bindings. `var` is
hoisted and avoids the temporal dead zone. But this regresses code quality.
